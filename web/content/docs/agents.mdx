An **agent** is a name you can call (`@terra`), a key that signs everything it does, and a
profile that says how to run it. Agents are reusable: the same terra works on many threads,
over months.

## Why named agents

Buzz gave agents names and keys; skills.sh turned skills into a one-line install. Together
they point at a better way to work than one assistant that knows everything:

- **Specialists.** `terra` builds, with the handful of skills your stack needs. `opus`
  reviews, with a review skill and a different model. You address each by name.
- **Real code review.** The best review comes from someone who didn't write the code. When
  terra is done it asks opus, on the same thread; opus's findings arrive as terra's next
  prompt, and you see the whole exchange. A different model catches different mistakes.
- **No skill bloat.** Installing every skill into one agent costs you on every session: each
  skill's description sits in its context, and the more there are, the more often the wrong
  one triggers. A named agent loads only its own.
- **Accountability.** Everything an agent does is signed with its key, and it has its own
  permissions, reach and daily budget.

## Create one

```bash
axel agent new terra codex --skills rust,axum
axel agent new opus claude/opus --skills review,security
axel agent ls
axel agent show terra       # profile, policy and the owner attestation
```

Creating an agent:

1. generates an **Ed25519 keypair** and stores the private key in the macOS keychain;
2. signs an **attestation** with your owner key: "this key is my agent terra";
3. records the profile.

The second word is what it runs: a harness and, after a `/`, its model. `claude` uses Claude
Code's default model, `claude/opus` picks Opus, `codex/gpt-5.5` a Codex model. Leave it out
and the agent runs Claude Code. The harnesses: `claude`, `codex`, `opencode`, `goose`,
`cursor`, `pi`, `omp`, `devin`, `grok`, `kimi`, `amp`, `hermes` and `openclaw` (see
[Installation](/docs/installation#harnesses)), or any other command. A custom command
speaking ACP runs as a managed session too.

| Profile | |
|---|---|
| `HARNESS[/MODEL]` | What it runs; `claude` by default. `--harness` and `--model` say the same as flags. |
| `--skills` | Skills to install for it, comma-separated, or `*` for all of them. |
| `--prompt` | A standing prompt added to every session. |
| `--color` | How it shows up in the dashboard and in `@mentions`. |
| `--runtime-mode` | How much it may do alone; see [Permissions and budgets](/docs/policies). |
| `--host` | Where it runs unless told otherwise; see [Remote hosts](/docs/remote-hosts). |

Change any of it later with `axel agent edit terra …`: `axel agent edit terra goose` moves
terra to Goose, `axel agent edit opus --model fable` changes only the model,
`axel agent edit terra --name sol` renames it (its key, policy and history stay; sessions
already running keep the old name until they restart), and `--skills`, `--prompt` and
`--color` replace those. `axel agent archive terra` retires an agent and keeps its key and
history.

### Custom ACP harnesses

Pass the entire ACP command as the harness and set the model separately:

```bash
axel agent new maki --harness 'maki acp'
axel agent new maki-fast --harness 'maki acp' --model 'opencode-go/deepseek-v4.1-flash'
```

Wrappers work too: `--harness 'fnox exec -- maki acp'`. Axel splits quoted command
arguments and starts the command directly, without a shell. The executable must
be installed and authenticated on the machine where the agent runs.

Axel selects models through ACP `configOptions` when the harness advertises a
model selector, including selectors grouped by provider. Older adapters keep
using `session/set_model`. Standard ACP usage updates populate the context gauge
and cumulative USD cost; the context gauge is not counted as billable tokens.

Prompts sent during a turn queue until it finishes. **Ctrl+S** cancels the current
turn and sends your new prompt. Harnesses can also opt into live steering with
`agentCapabilities._meta.axel.steer: true` and the `_axel/steer` extension described
in the [design document](https://github.com/lgalabru/axel/blob/main/docs/DESIGN.md#managed-runtime-acp-and-the-thread-view).
This is capability-based and works for custom harnesses as well as the built-ins.

## Why keys

Everything an agent does on a thread (a reply, a tool call, a message to another agent) is
an event signed with its key. That makes three things possible:

- **Attribution you can check.** A thread shows who did what, and a copy of it on another
  machine can verify that it was really terra.
- **Safe delegation.** On a remote machine, terra's key never leaves home: the machine gets a
  short-lived grant to sign for it on one thread. See [Remote hosts](/docs/remote-hosts#keys-never-leave-home).
- **Multiplayer threads.** Threads merge across machines and people by their signed events.

## Inside a session

Axel tells the agent who it is through its environment:

| Variable | |
|---|---|
| `AXEL_AGENT_NAME` | Its name. |
| `AXEL_AGENT` | Its public key. |
| `AXEL_THREAD` | The thread it works on. |
| `AXEL_SESSION` | This session. |

It also installs the **axel skill**, which teaches the agent how to message other agents,
report its status and read its inbox, and an **MCP server** with the same tools. See
[The agent's toolkit](/docs/agent-toolkit).

## Inbox

Every identity, you included, has an inbox: messages that mention it, permission requests,
questions, and status from its sessions. `axel inbox` prints yours;
`axel inbox --agent terra` prints terra's. When anything needs you, `axel` opens on the
inbox instead of the launcher.
